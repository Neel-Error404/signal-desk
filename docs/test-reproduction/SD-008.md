# SD-008 Azure-Hosted Staging Baseline Verification Plan

**Status:** IN PROGRESS — local implementation only; hosted proof remains unexecuted

## Claim under test

One exact protected SignalDesk `main` revision can be rebuilt into an attested public GHCR OCI
digest, migrated and deployed into an Entra-protected ephemeral Azure Container Apps staging
environment backed by private Azure PostgreSQL, observed through Azure evidence, returned to its
prior healthy staging revision, exported as a durable redacted proof packet, and removed as an
active cost-bearing environment without exposing secrets, real customer data, or production
authority.

## Claims that remain forbidden

- production readiness or production deployment;
- product authentication or tenant authorization;
- autonomous merge, deployment, promotion, or rollback;
- canonical L2, P5.2 activation, L3, canary authority, or qualification-period credit;
- multi-region availability, automatic database rollback, or customer-data durability;
- a persistent staging URL, retained staging database, or always-on runtime.

## Provider preflight gates

Before any Azure or GitHub mutation, verify:

1. repository, main commit, visibility, ruleset, required check, worktree, and Git identity;
2. Central India provider registrations, Container Apps environment quota, PostgreSQL
   version/SKU/zone availability, subnet capacity, Key Vault/private endpoint quota, and Log
   Analytics availability;
3. exact global resource-name availability;
4. live ephemeral-session cost estimate, sponsorship budget impact, USD 5 budget alert, and
   deletion authority for the exact resource group;
5. GitHub public-repository Environment reviewer and protected-branch enforcement;
6. exact OIDC issuer/audience/subject and custom role actions;
7. Entra application ownership, allowed owner, smoke identity, token audience, and anonymous
   denial configuration;
8. private PostgreSQL DNS resolution and routing from the Container Apps environment;
9. secret generation, masking, Key Vault RBAC, runtime/migration separation, rotation plan, and
   public-image scan for secrets or private runtime material;
10. Bicep `what-if` contains only the approved staging resources and no deletion or replacement of
    unrelated resources.

The approved design uses four independently reviewed Environments: GitHub-only
`staging-publication`, then Azure `staging-provision`, `staging-traffic`, and `staging-teardown`.
A single approval cannot authorize all four consequences. Provision, traffic, and teardown use
three separate OIDC service principals so provider permissions cannot aggregate.

Any mismatch blocks implementation. Do not reuse another project's resource, open PostgreSQL
publicly, broaden OIDC, or upgrade SKU/cost automatically.

## Hosted positive proof

1. Owner dispatches the exact protected main revision and the full ordered ladder passes.
2. Two normalized clean builds produce the same application-tree and OCI manifest digests; image
   secret/private-material scan, SBOM, vulnerability scan, provenance, private GHCR digest, and Git
   revision agree.
3. Owner separately changes the exact package to public and approves `staging-publication`;
   anonymous pull and application-tree equality pass.
4. Owner approves `staging-provision`; GitHub OIDC matches the exact provision subject.
5. Bicep deployment matches the approved what-if.
6. The same digest runs the successful role-bootstrap job and then Prisma migration job.
7. A zero-traffic candidate revision becomes healthy.
8. Anonymous ingress is denied and exact Entra owner/smoke identities are accepted.
9. Both health endpoints and the full owner workflow pass with synthetic data.
10. Logs and provider records contain the expected correlation/revision/deployment identifiers and
    no secret-shaped output.
11. Owner approves `staging-traffic`; the exact candidate receives 100%.
12. The controlled same-digest revision and rollback rehearsal restore the prior healthy revision.
13. Final traffic, health, access, logs, database, image digest, and provider state are reread.
14. Redacted public evidence and the owner-controlled private evidence digest are exported outside
    the disposable resource group and independently reopened.
15. Owner approves `staging-teardown`; the exact staging resource group is deleted.
16. Azure inventory, endpoint, database, active Key Vault, network, DNS-link, log-workspace, and
    resource-scoped identity rereads prove active/billable absence. The purge-protected Key Vault
    tombstone and any provider retention record are captured with expiry. Any active orphan,
    unexpected charge, accessible secret, or reachable URL fails the proof.

## Controlled negative proofs

| Failure | Required observation | Forbidden outcome |
|---|---|---|
| Anonymous request | Entra denies before product response | Public product content |
| PostgreSQL path unavailable | Liveness bounded; readiness `503` | Traffic promotion or secret output |
| Migration job failure | Terminal failed job bound to digest | Candidate creation or traffic change |
| Unauthorized/mutable image | Contract rejection before provider call | Container Apps revision |
| Candidate readiness failure | Zero traffic and explicit failure | Promotion or current-revision change |
| Missing/stale telemetry | Verification failure | Acceptance based on absent evidence |
| Rollback rehearsal | Prior revision restored and healthy | Production action or database reversal |
| Teardown incomplete | Explicit active-orphan, charge, accessible-secret, reachable-endpoint, or unaccounted-tombstone failure | SD-008 closure or silent retention |

## Learning proof

After hosted teardown evidence is complete, copy only redacted evidence to an external quarantine.
At most one candidate may be proposed. The candidate owner cannot be the evaluator, the evaluator
cannot approve or promote, and an exact human approval or rejection must bind the candidate state
and evaluation digests. An approval may issue only a non-mutating promotion packet. Journal replay,
foreign-key integrity, artifact bytes, observations, evaluation, decision, and packet must agree.

## Final verdict rule

`VERIFIED` requires every deterministic local level, provider preflight, positive proof, controlled
negative proof, human approval, immutable binding, redaction check, rollback observation, evidence
export, teardown approval, zero-active-resource verification, and deletion-tombstone accounting to
pass for the same exact staging deployment chain. `VERIFIED` for the declared two-lane slice also
requires the bounded learning decision and replay. One missing operand yields `BLOCKED` or
`IMPLEMENTED`, never a staging-readiness claim.

The final handoff must state the exact resources and evidence, what remains absent, session cost,
deleted data/resources, the formerly active revision and rollback target, post-delete verification,
and the explicit prohibition on production, P5.2, canonical L2, L3, and qualification-period
credit.
