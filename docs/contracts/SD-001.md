# SD-001 Public HTTP and Domain Contract

**Version:** 1

**Status:** Ratified design; not implemented

**Change class:** `public-contract`

**Owner:** Neel

**Runtime boundary:** local-only

## Contract claim

This document specifies the first local SignalDesk feedback-to-signal slice. It is a design and
compatibility contract, not evidence that an endpoint, database, detector, UI, deployment, or
security control is operational.

The contract provides no authentication, authorization, verified identity, tenant isolation,
hosted-operation, production-readiness, or complete-DLP claim. The service must bind to a local
operator-controlled environment. Exposing it to a shared or public network is outside SD-001.

## Bounded contexts

### Feedback Intake

Owns acceptance of bounded feedback, the explicit content acknowledgement, deterministic
restricted-content checks, and the immutable Feedback source record.

### Signal Inbox

Owns the canonical Signal, its required source Feedback lineage, append-only TriageEvent history,
and the current inbox projection.

### Feedback-to-signal workflow

Coordinates public application ports from both contexts. It creates Feedback and Signal in one
database transaction. It contains orchestration only and owns no domain record.

## Common HTTP rules

- Base path: `/api/v1`.
- Media type: `application/json; charset=utf-8` for request and response bodies.
- Uploads, multipart requests, binary bodies, attachments, and remote URLs are unsupported.
- Maximum request body: 16 KiB (16,384 bytes). An absent or invalid `Content-Length` does not bypass
  streaming byte-count enforcement.
- Request objects are closed: unknown properties are rejected.
- IDs are server-generated UUIDs and timestamps are server-generated UTC RFC 3339 values.
- A caller-provided `X-Correlation-Id` is accepted only when it satisfies the bounded correlation
  format; otherwise the server replaces it. Correlation values are not authorization credentials.
- Errors use the envelope below and never echo submitted confidential content.

```json
{
  "error": {
    "code": "content_acknowledgement_required",
    "message": "Set contentAcknowledged to true before submitting content.",
    "details": {
      "fields": ["contentAcknowledged"]
    },
    "correlationId": "server-generated-bounded-id"
  }
}
```

No endpoint silently truncates, sanitizes, retries, or falls back to probabilistic processing.

## Domain records and invariants

### Feedback

| Field | Contract |
|---|---|
| `id` | Server-generated UUID; immutable |
| `content` | 1 to 8,000 Unicode code points after line-ending normalization; immutable |
| `createdAt` | Server-generated UTC timestamp; immutable |

Feedback content remains confidential. Whitespace-only content is invalid. Unicode normalization
must not change the semantic source text; only CRLF and CR line endings are normalized to LF for
deterministic storage and counting.

### Signal

| Field | Contract |
|---|---|
| `id` | Server-generated UUID; immutable |
| `feedbackId` | Required Feedback UUID; immutable and unique |
| `statement` | Deterministically copied from the accepted Feedback content; immutable in SD-001 |
| `createdAt` | Server-generated UTC timestamp; immutable |
| `revision` | Non-negative triage projection revision |
| `state` | Projection of ordered triage events; initially `new` |

For every committed Feedback created by the submission workflow, exactly one committed Signal
exists with the same source lineage. `Signal.feedbackId` is protected by a database unique
constraint. Both records commit in one PostgreSQL transaction or neither commits.

SD-001 does not group, merge, deduplicate, summarize, classify, or synthesize feedback.

### TriageEvent

| Field | Contract |
|---|---|
| `id` | Server-generated UUID; immutable |
| `signalId` | Required Signal UUID; immutable |
| `sequence` | Monotonic integer unique within the Signal |
| `fromState` | State at the required prior revision |
| `toState` | One of `new`, `reviewing`, `accepted`, `rejected` |
| `rationale` | 1 to 2,000 Unicode code points; immutable |
| `operatorLabel` | 1 to 120 Unicode code points; an unverified local label |
| `createdAt` | Server-generated UTC timestamp; immutable |

TriageEvent is append-only. There is no update or delete contract. The current Signal state and
revision are derived from the ordered event sequence. The operator label records what the local
operator supplied; it is not an authenticated or verified identity.

## Endpoints

### `POST /api/v1/feedback`

Creates one Feedback and its one Signal.

Request:

```json
{
  "content": "The export loses the selected date range.",
  "contentAcknowledged": true
}
```

Requirements:

- `content` is required and must satisfy the Feedback bounds.
- `contentAcknowledged` is required and must be the literal boolean `true`.
- Restricted-content checks run before any domain record is persisted.

Success: `201 Created`.

```json
{
  "feedback": {
    "id": "uuid",
    "content": "The export loses the selected date range.",
    "createdAt": "2026-08-16T00:00:00Z"
  },
  "signal": {
    "id": "uuid",
    "feedbackId": "uuid",
    "statement": "The export loses the selected date range.",
    "state": "new",
    "revision": 0,
    "createdAt": "2026-08-16T00:00:00Z"
  }
}
```

The response is returned only after the atomic transaction commits.

### `GET /api/v1/signals`

Returns an inbox page ordered by `(createdAt DESC, id DESC)`.

Query parameters:

- `limit`: optional integer, default 25, minimum 1, maximum 100.
- `cursor`: optional opaque cursor emitted by the preceding response; maximum 512 bytes.

Success: `200 OK` with `{ "items": [...], "nextCursor": "opaque-or-null" }`. Each item contains
the Signal fields and source `feedbackId`; it does not include a triage history or raw detector
output.

### `GET /api/v1/signals/{signalId}`

Returns one Signal, its source Feedback, and its ordered TriageEvent history. Success is `200 OK`.
An unknown well-formed ID returns `404 Not Found`; a malformed ID returns `400 Bad Request`.

### `POST /api/v1/signals/{signalId}/triage-events`

Appends one human-requested triage event.

Request:

```json
{
  "expectedRevision": 0,
  "toState": "reviewing",
  "rationale": "Confirm impact with the reporting workflow owner.",
  "operatorLabel": "Neel",
  "contentAcknowledged": true
}
```

Requirements:

- `expectedRevision` is a required non-negative integer and must match the current projection.
- `toState`, `rationale`, and `operatorLabel` are required and bounded by the TriageEvent contract.
- `contentAcknowledged` must be the literal boolean `true` because rationale and operator label are
  persisted content.
- The same restricted-content controls used by feedback intake run before persistence.

Success: `201 Created` with the immutable event and the resulting Signal state and revision. A
revision mismatch returns `409 Conflict`; it never overwrites the competing event.

## Content rejection boundary

Before any content-bearing write, deterministic versioned rules reject only configured
high-confidence matches, including:

- PEM-encoded private-key material;
- recognized credential/token formats with strong fixed prefixes and valid structural bounds;
- payment-card numbers that satisfy issuer-length rules and a Luhn checksum;
- explicitly configured regulated identifiers whose format provides a comparably high-confidence
  match.

A rejection returns `422 Unprocessable Entity` with code `restricted_content_detected` and
non-sensitive rule identifiers. The matched value, surrounding content, and detector internals are
not returned or logged.

The rule set is intentionally incomplete. It is not a general secret scanner, a complete regulated
data classifier, or complete DLP. The product remains unsuitable for credentials, regulated data,
or proprietary source-code uploads. Uncertain content is not silently rewritten; operators remain
responsible for what they submit.

## Error contract

| Status | Code | Condition |
|---|---|---|
| 400 | `invalid_json` | Body is not valid JSON |
| 400 | `invalid_request` | Closed schema, field type, UUID, cursor, or state is invalid |
| 413 | `input_too_large` | Byte or field bound is exceeded |
| 415 | `unsupported_media_type` | Request is not UTF-8 JSON |
| 422 | `content_acknowledgement_required` | Required acknowledgement is absent or not `true` |
| 422 | `restricted_content_detected` | A configured high-confidence rule matches |
| 404 | `signal_not_found` | A well-formed Signal ID does not exist |
| 409 | `lineage_conflict` | The one-to-one lineage constraint would be violated |
| 409 | `revision_conflict` | Triage append uses a stale revision |
| 503 | `storage_unavailable` | PostgreSQL transaction cannot be completed |
| 500 | `internal_error` | An unexpected failure occurs |

Errors are explicit and actionable. Database or detector failures fail the write closed; they do
not downgrade validation or create a partial record.

## Persistence contract

- Prisma repositories are the only path from application code to PostgreSQL.
- HTTP handlers do not import Prisma.
- Feedback and Signal creation share one transaction boundary.
- Database constraints enforce Feedback and Signal primary keys, unique `Signal.feedbackId`, and
  unique `(signalId, sequence)` TriageEvent ordering.
- Triage writes use a revision predicate in the transaction to prevent lost updates.
- No SD-001 public endpoint updates or deletes Feedback, Signal, or TriageEvent records.
- Schema migration, retention, backup, and destructive cleanup require separately reviewed work;
  this contract does not claim those operational capabilities exist.

## Observability and privacy contract

Permitted telemetry contains route template, method, status class, latency, bounded correlation ID,
error code, and aggregate detector rule ID. Logs, traces, and metrics must not contain feedback,
signal statements, rationale, operator labels, credentials, cookies, authorization values, request
bodies, or response bodies.

Correlation is diagnostic only and grants no authority. Telemetry configuration is not evidence of
successful operation until executable evidence exists.

## Compatibility

Adding an optional response field is compatible only when existing clients can ignore it. Removing
or renaming a field, changing a bound or invariant, weakening rejection, changing error semantics,
adding authentication assumptions, or changing one-to-one lineage is a public-contract change and
requires architecture-owner and code-owner approval plus compatibility evidence and a migration
plan.

Neel retains merge, release, deployment, learning-promotion, and architecture-exception authority.
