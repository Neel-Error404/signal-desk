# SD-002 Manual Signal-to-Prioritized-Issue Contract

**Version:** 1

**Status:** Ratified bounded implementation contract

**Change class:** `public-contract`

**Owner:** Neel

**Runtime boundary:** local-only

## Contract claim

SD-002 adds one deterministic manual promotion: a currently accepted Signal can create one
immutable prioritized Product Issue while preserving its Feedback and Signal lineage.

This contract does not provide authentication, authorization, verified identity, tenancy,
hosting, deployment, production readiness, automatic prioritization, or complete DLP.

All common HTTP, content, privacy, correlation, and error-envelope rules in SD-001 continue to
apply.

## Product Issue record

| Field | Contract |
|---|---|
| `id` | Server-generated UUID; immutable |
| `signalId` | Required source Signal UUID; immutable and unique |
| `sourceSignalRevision` | Exact non-negative Signal revision used for promotion |
| `title` | 1 to 200 Unicode code points; immutable |
| `priority` | `low`, `medium`, `high`, or `critical`; immutable |
| `rationale` | 1 to 2,000 Unicode code points; immutable |
| `operatorLabel` | 1 to 120 Unicode code points; unverified local label; immutable |
| `createdAt` | Server-generated UTC RFC 3339 timestamp; immutable |

The source Signal must be `accepted` when the transaction evaluates promotion, and its revision
must equal `expectedSignalRevision`. One Signal may have at most one Product Issue.

## `POST /api/v1/signals/{signalId}/product-issue`

Request:

```json
{
  "expectedSignalRevision": 2,
  "title": "Preserve the selected date range during export",
  "priority": "high",
  "rationale": "The confirmed reporting workflow loses an explicit user selection.",
  "operatorLabel": "Neel",
  "contentAcknowledged": true
}
```

Requirements:

- the request object is closed;
- `expectedSignalRevision` is a non-negative integer;
- title, rationale, and operatorLabel satisfy their code-point bounds;
- priority is one of the four declared values;
- `contentAcknowledged` is the literal boolean `true`;
- deterministic restricted-content checks run before persistence;
- the source Signal exists, is currently `accepted`, and has the expected revision;
- no Product Issue already exists for that Signal.

Success is `201 Created` and returns:

```json
{
  "productIssue": {
    "id": "uuid",
    "signalId": "uuid",
    "sourceSignalRevision": 2,
    "title": "Preserve the selected date range during export",
    "priority": "high",
    "rationale": "The confirmed reporting workflow loses an explicit user selection.",
    "operatorLabel": "Neel",
    "createdAt": "2026-08-17T00:00:00.000Z"
  },
  "lineage": {
    "feedbackId": "uuid",
    "signalId": "uuid",
    "signalRevision": 2
  }
}
```

## Signal detail compatibility

`GET /api/v1/signals/{signalId}` retains all SD-001 fields and adds:

```json
{
  "productIssue": null
}
```

or the serialized Product Issue. Existing clients may ignore this additive field.

## Error additions

| Status | Code | Condition |
|---|---|---|
| 409 | `signal_not_accepted` | The Signal is not currently accepted |
| 409 | `revision_conflict` | The Signal revision differs from `expectedSignalRevision` |
| 409 | `product_issue_exists` | The Signal already has a Product Issue |

All SD-001 request, content, storage, and internal error codes remain applicable.

## Persistence and immutability

- Prisma is the only application database adapter.
- Eligibility and creation execute in one PostgreSQL transaction while the source Signal row is
  locked.
- PostgreSQL enforces unique `ProductIssue.signalId` and the Signal foreign key.
- A database trigger rejects ProductIssue update or delete.
- No SD-002 endpoint updates or deletes a Product Issue.

## Non-claims

SD-002 does not group feedback, infer priority, manage an issue lifecycle, assign work, create a
pull request, deploy, release, or communicate a fix. The `reviewable-pr` target applies to delivery
of this product change, not to Product Issue behavior.
