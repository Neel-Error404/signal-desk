## Verified product outcome

A local operator can use only the product interface to:

1. capture Feedback and create its canonical Signal;
2. append manual triage until the Signal is accepted;
3. promote that accepted Signal into one prioritized Product Issue;
4. record a manual title, priority, rationale, and unverified local operator label;
5. inspect the exact Feedback, Signal, and source Signal revision lineage; and
6. reload the application and observe the persisted immutable issue.

The implementation does not group feedback, infer priority, manage issue status, assign work,
create implementation tasks, deploy, release, or communicate a fix.

## Implementation evidence

- `Product Issues` is a separate bounded context with inward dependency direction.
- The `signal-to-issue` workflow coordinates public application ports.
- PostgreSQL locks the source Signal row while checking state and revision.
- Only a currently accepted Signal at the exact expected revision is eligible.
- `ProductIssue.signalId` is unique and binds the exact source Signal revision.
- A PostgreSQL trigger rejects Product Issue update and delete.
- The additive Signal-detail response includes the Product Issue or `null`.
- The new POST endpoint uses the existing closed UTF-8 JSON, 16 KiB, acknowledgement,
  restricted-content, privacy, and explicit-error boundaries.
- The desktop and mobile workflow creates, displays, reloads, and preserves the issue.
- The optimized Next.js build includes the Product Issue route.
- `npm audit` reports zero vulnerabilities.
